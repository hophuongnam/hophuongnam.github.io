What is a Tag Manager?

A tag manager is a platform that lets marketing teams add tracking scripts to your website without deploying code changes. You add one "container" script, and then anyone with dashboard access can inject additional scripts (analytics, ads, chat widgets, A/B tests) that go live immediately.

Common Examples:
Google Tag Manager (GTM) Adobe Launch Tealium Segment Ensighten

Why It's the Highest Risk for PCI DSS

  • Anyone with dashboard access can inject ANY JavaScript onto your payment page
  • Scripts can read form inputs (including card numbers), cookies, and page content
  • Changes bypass your code review, security testing, and deployment process
  • A compromised tag manager account = compromised payment page
  • CSP only limits WHERE scripts load from, not WHAT they do once loaded
  • You may not know what scripts are actually running on your page
Strong Recommendation:

Remove tag managers from payment pages entirely. Use server-side tagging (GTM Server-Side, Segment Functions) or direct API calls from your backend for analytics needs.

Key Takeaways

SRI Only for static external scripts (1st-party or versioned 3rd-party). Hash the file at deploy time.
Nonce For dynamic scripts (1st-party external or inline). Can't inject nonce into 3rd-party responses.
CSP Hash Best for inline static scripts. Hash IS the integrity—any change requires new hash in CSP.
Domain For auto-updating 3rd-party, CSP domain allowlist is often the only option. Requires monitoring.

⚠ High-Risk Configuration

Content-Security-Policy
  • Fetch Directives (Control resource loading)
  • default-src Fallback for all fetch directives not explicitly set. 'none' blocks everything by default, requiring explicit allowlisting. This is the recommended secure starting point.
  • script-src Controls which scripts can execute. Key values: 'self' (same origin), 'nonce-xxx' (server-generated token), 'sha256-xxx' (hash of inline script), or specific domains. Critical for 6.4.3 compliance.
  • style-src Controls which stylesheets can be applied. 'self' allows same-origin styles. 'unsafe-inline' allows inline styles (less secure, sometimes needed for third-party widgets).
  • img-src Controls which images can load. https: allows any HTTPS image, data: allows base64-encoded images. Common for payment page logos and icons.
  • font-src Controls which fonts can load. Usually 'self' or CDN domains like Google Fonts.
  • connect-src Controls destinations for fetch(), XMLHttpRequest, WebSocket, and EventSource. Must include API endpoints your scripts call (e.g., https://api.stripe.com).
  • frame-src Controls which URLs can be loaded in iframes. Payment providers like Stripe often use iframes for secure card input fields.
  • Document Directives (Control document properties)
  • base-uri Restricts URLs for the <base> element. Set to 'self' to prevent attackers from changing the base URL for relative links.
  • form-action Restricts URLs that forms can submit to. 'self' prevents form hijacking where attackers redirect form data to malicious servers.
  • frame-ancestors Controls which sites can embed your page in an iframe. 'none' prevents clickjacking attacks. Replaces X-Frame-Options header.
  • Reporting Directives (Monitor violations)
  • report-uri URL to receive JSON reports when CSP is violated. Essential for 11.6.1 monitoring. Reports include blocked resource, violated directive, and page URL.
  • Source Values (Used in directives)
  • 'self' Matches the page's own origin (scheme + host + port). The most common starting point for secure policies.
  • 'none' Blocks all sources. Used in default-src to create a deny-by-default policy.
  • 'nonce-{value}' Allows scripts/styles with matching nonce attribute. Must be cryptographically random (128+ bits) and unique per page load. For dynamic scripts.
  • 'sha256-{hash}' Allows inline scripts/styles matching the hash. Content must be identical (including whitespace). For static inline scripts.
  • 'unsafe-inline' Allows all inline scripts/styles. AVOID for scripts - defeats XSS protection. Sometimes needed for styles with third-party widgets.
  • https://domain.com Allows resources from specific domain. Be specific - avoid wildcards like *.example.com which expand attack surface.
HTML
  • Script Loading Attributes
  • src URL of external script file. Can be relative (/js/app.js) or absolute (https://cdn.example.com/lib.js). For PCI DSS, document all script sources in your inventory.
  • async Script downloads in parallel and executes as soon as available, without blocking HTML parsing. Order not guaranteed. Good for independent analytics scripts.
  • defer Script downloads in parallel but executes after HTML parsing completes, in document order. Good for scripts that need the DOM ready.
  • Subresource Integrity (SRI)
  • integrity Cryptographic hash of expected script content. Format: sha384-{base64hash}. Browser blocks script if hash doesn't match. Critical for 6.4.3 integrity verification. Generate with: openssl dgst -sha384 -binary file.js | openssl base64 -A
  • crossorigin Required when using integrity with cross-origin scripts. Value anonymous sends no credentials. Enables CORS error reporting. Without this, SRI failures are silent.
  • CSP Nonce
  • nonce Server-generated random token that must match CSP header's 'nonce-xxx' value. Must be unique per page load, cryptographically random (min 128 bits). Authorizes script execution without relying on content hash.
  • Security Attributes
  • type="module" Treats script as ES6 module. Modules are deferred by default, have strict mode enabled, and support import/export. CORS required for cross-origin modules.
  • nomodule Script only runs in browsers that don't support ES6 modules. Used for fallback scripts serving older browsers.
  • SRI Hash Algorithms
  • sha256 Minimum recommended hash algorithm. Fast to compute. Example: integrity="sha256-abc123..."
  • sha384 Recommended balance of security and performance. Most commonly used for SRI. Example: integrity="sha384-xyz789..."
  • sha512 Strongest hash, slightly slower. Use when maximum security is required. Example: integrity="sha512-def456..."
Python
  • PCI DSS 11.6.1 Requirements
  • Change Detection Mechanism to detect unauthorized modifications to HTTP headers and script content on payment pages. Must alert personnel to investigate changes.
  • Frequency Monitoring must occur at least weekly, but more frequent monitoring (hourly, daily) is recommended for higher-risk configurations. High-risk setups may need real-time monitoring.
  • Alerting Changes must trigger alerts to security personnel within a defined timeframe. Document your alert thresholds and response procedures.
  • Monitoring Levels
  • Basic (Headers) Monitors HTTP security headers (CSP, HSTS, X-Frame-Options). Low overhead, catches policy changes. Suitable for first-party static scripts.
  • Content Monitors headers plus external script file content via hash comparison. Detects when third-party vendors update their scripts. Medium overhead.
  • Full Page Parses HTML to detect new scripts, monitors headers and content. Catches injected scripts from compromised third-parties. Highest coverage for tag manager scenarios.
  • Headers to Monitor
  • Content-Security-Policy Critical for 6.4.3. Changes could allow unauthorized scripts. Any modification should trigger immediate investigation.
  • Strict-Transport-Security HSTS header. Removal could enable downgrade attacks. Monitor for weakened or removed max-age values.
  • X-Frame-Options Clickjacking protection. Changes could enable UI redress attacks on payment forms.
  • X-Content-Type-Options Should be nosniff. Prevents MIME type sniffing attacks.
  • CSP Violation Reporting
  • report-uri Endpoint receiving JSON violation reports. Deprecated but widely supported. Format: report-uri https://yoursite.com/csp-reports
  • report-to Modern reporting API using Reporting-Endpoints header. More flexible but less browser support. Use both for compatibility.
  • Report Contents Reports include: blocked URI, violated directive, document URI, source file, line number. Use to identify unauthorized script attempts.
  • Implementation Options
  • Cron Job Simple scheduled task running monitoring script. Example: 0 * * * * python monitor.py runs hourly. Good for basic/content monitoring.
  • Commercial Tools Jscrambler, PerimeterX, Akamai Page Integrity Manager. Provide real-time monitoring, detailed analytics, and managed alerting for high-risk scenarios.
  • Report Collector Service to receive and analyze CSP violation reports. Can be self-hosted or use services like report-uri.com, Sentry, or custom webhook endpoints.
